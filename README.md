# LisPython
[![PyPI version](https://badge.fury.io/py/lispython.svg)](https://badge.fury.io/py/lispython)

LisPython is a Lisp-flavored syntax for Python with Lisp-style macros. Source files (`.lpy`) are transpiled to Python and executed on the standard CPython runtime.

## Documentation
Full documentation lives at [https://jetack.github.io/lispython/](https://jetack.github.io/lispython/).

## Quick Start
```lisp
(import math)

(def area [r]
  (return (* math.pi (** r 2))))

(print (area 3))
```
```bash
lpy example.lpy
```


## How to Run LisPython code
### Run from source
```bash
lpy {filename}.lpy
```

### Run REPL
```bash
lpy
# or
lpy -t # if you want to print python translation.
```

### Show translation
```bash
l2py {filename}.lpy
```
Prints the translated Python to stdout. It does not execute the code.

### Run Tests
```bash
# in project root directory
pytest
# or
lpy -m pytest
```

## LSP Server
LisPython ships with a language server (`lpy-lsp`) that speaks LSP over stdio. It provides:

- Diagnostics: parse and compile errors, plus the Python backend's (type errors, undefined names, unused code) placed on the `.lpy` code they concern
- Completions: special forms and macros, plus the Python backend's names (attributes, scopes, imports); without a backend, special forms, macros, builtins and the file's own definitions
- Hover and signature help: lispython's forms and macros answered locally, Python names through the backend (builtins without one)
- Document symbols and workspace symbol search
- Go-to-definition, including across `.lpy` files in the workspace

`pip install "lispython[lsp]"` adds basedpyright, a Python language server the LSP runs over the compiled code of each workspace project; `pip install "lispython[lsp-pyrefly]"` adds pyrefly. The `backend` initialization option picks one: `"basedpyright"`, `"pyrefly"` or `"off"`; without it, basedpyright when installed, else pyrefly when installed, else off.

The backend's diagnostics are shown on the `.lpy` buffer: opening a buffer starts the backend, and a diagnostic that lands on code the buffer never spells (generated by `require`, `defmacro`, the prelude) is dropped; an error inside a macro's output is shown on the macro call. A buffer that does not parse or compile shows only that error. The `pythonDiagnostics` initialization option (default `true`) set to `false` turns them off, and the backend then starts only on the first request that needs it. A line comment of the running backend's tool, `; pyrefly: ignore[codeA, codeB]` under pyrefly or `; pyright: ignore[ruleA, ruleB]` under basedpyright, drops the backend's diagnostics of those codes that start on its line, and a bare `; pyrefly: ignore` / `; pyright: ignore` all of them (spaced as the tool takes it: `;pyrefly:ignore` and `;; pyrefly: ignore` work too); each backend honours only its own tool's comments, and lispython's own parse and compile errors are never suppressed. An ignore comment that suppresses nothing is never reported. Under basedpyright the rules follow the project's own `pyrightconfig.json`, else `[tool.basedpyright]`, else `[tool.pyright]` in `pyproject.toml`: `typeCheckingMode` (default `"standard"`), every `report*` rule and the `strict*` inference settings; path settings are ignored. Under pyrefly they follow the project's `pyrefly.toml`, else `[tool.pyrefly]` in `pyproject.toml` (its rule keys and `errors` table; path settings are ignored). A project with neither, or whose config cannot be read or is refused by the installed pyrefly (the LSP log says why), is checked with pyrefly's `"default"` preset; the server says so, and why, once per project when its backend starts, and adding or fixing the config (e.g. `preset = "default"`) chooses the preset.

## nREPL Server
LisPython includes an nREPL server for REPL-driven development:

```bash
lpy --nrepl         # start on a random port
lpy --nrepl 7888    # start on a specific port
```

While running, the server writes its port to `.nrepl-port` in the working directory for editor auto-discovery.

The server accepts newline-delimited JSON over TCP and supports:
- `eval` — evaluate LisPython code, return value/stdout/error
- `load-file` — load a `.lpy` file into the session
- `"stream": true` on an `eval` or `load-file` makes it a stream eval: its output arrives while it runs as `{"op": "out", "stdout": text}` / `{"op": "out", "stderr": text}` messages carrying the request's `id`, in write order, before the final result (whose `stdout` is then `""`). Without it the eval answers once, output in its result. Either way the connection keeps answering every other request while an eval runs, so a later `complete`, `macroexpand` or `docs` may see the scope as it was before an earlier eval, and replies can come in another order than their requests: match them by `id` (an `id` already queued or running is refused; an id-less eval's reply has nothing to match by). One connection's evals run one at a time in request order; connections run at once. Closing the connection, or half-closing it (EOF), cancels or interrupts its unfinished evals, whose replies are then usually lost.
- `interrupt` — `{"op": "interrupt", "interrupt-id": X}` stops the eval `X` (stream or plain) on this connection: a running one gets a `KeyboardInterrupt` (its result's `error` is the traceback; code blocked in one C call stops when the call returns), a queued one never runs (its result's `error` is `"KeyboardInterrupt"`). Replies `{"op": "interrupt-result", "interrupt-id": X}`, or an error when no such eval is queued or running.
- Threads: a thread the evaluated code starts prints to the server's own stdout/stderr (the terminal or editor buffer running `lpy --nrepl`), never into the eval's result or `out` messages, as in a plain Python REPL; `interrupt` stops only the eval's own thread, never threads it started.
- `macroexpand` — expand macros and return the result
- `complete` — prefix and dot-completion from the live scope. `items` lists one LSP-shaped item per name, in `completions` order: `{"label": label, "kind": n, "filterText": text}`, `n` the LSP CompletionItemKind number (Class 7, Function 3, Variable 6, Keyword 14), `text` the typed word plus the rest of the label, plus `"labelDetails": {"description": tag}` only for a name lispython tags (`special form` with Keyword, `macro` and `function` with Function), as the LSP server sends them. The server filters by the LSP's rule (case-insensitive prefix, with `-` and `_` matching each other after a letter or digit), so a client's own prefix match on `filterText` keeps every item. A label is spelled as the LSP labels it (`ok?` when the evaluated code wrote that, else `my-name`) and is only the part after the prefix's last `.` (`heapq.nl` offers `nlargest`); `word` is the typed text every label replaces (`nl`; the whole prefix when it has no `.`), so a client replaces that many characters before the cursor. `completions` is the full name list (`heapq.nlargest`), one per item in the same order; there is no `kinds` map.
- `docs` — signature and docstring for a symbol
- `annotate` — type tag (function/class/module/macro)

### Editor setup

#### VS Code
Install the [LisPython](https://marketplace.visualstudio.com/items?itemName=jetack.vscode-lispython) extension. It connects to both LSP and nREPL automatically.

#### Emacs
Use [`lpy-mode`](https://github.com/jetack/lpy-mode). It provides nREPL integration (eval, completion, eldoc, macroexpand) and LSP via eglot.
