# LisPython
[![PyPI version](https://badge.fury.io/py/lispython.svg)](https://badge.fury.io/py/lispython)

LisPython is a Lisp-flavored syntax for Python with Lisp-style macros. Source files (`.lpy`) are transpiled to Python and executed on the standard CPython runtime.

## Documentation
Full documentation lives at [https://jetack.github.io/lispython/](https://jetack.github.io/lispython/).

## Quick Start
```lisp
(import math)

(def area [r]
  (return (* math.pi (** r 2))))

(print (area 3))
```
```bash
lpy example.lpy
```

## Installation
### Using pip
```bash
pip install lispython
```

### Manual Installation (for development)
```bash
uv sync # install dependencies
uv pip install -e . # for development
```

Contributors using git worktrees: run `git config core.hooksPath .githooks` once in the main checkout; see [`.githooks/README.md`](.githooks/README.md). This replaces `.git/hooks`, so hooks installed there stop running.

## How to Run LisPython code
### Run from source
```bash
lpy {filename}.lpy
```

### Run REPL
```bash
lpy
# or
lpy -t # if you want to print python translation.
```

### Show translation
```bash
l2py {filename}.lpy
```
Prints the translated Python to stdout. It does not execute the code.

### Run Tests
```bash
# in project root directory
pytest
# or
lpy -m pytest
```

## LSP Server
LisPython ships with a language server (`lpy-lsp`) that speaks LSP over stdio. It provides:

- Diagnostics: parse and compile errors, plus the Python backend's (type errors, undefined names, unused code) placed on the `.lpy` code they concern
- Completions: special forms and macros, plus the Python backend's names (attributes, scopes, imports); without a backend, special forms, macros, builtins and the file's own definitions
- Hover and signature help: lispython's forms and macros answered locally, Python names through the backend (builtins without one)
- Document symbols and workspace symbol search
- Go-to-definition, including across `.lpy` files in the workspace

`pip install "lispython[lsp]"` adds pyrefly, a Python language server the LSP runs over the compiled code of each workspace project; `pip install "lispython[lsp-basedpyright]"` adds basedpyright. The `backend` initialization option picks one: `"pyrefly"`, `"basedpyright"` or `"off"`; without it, pyrefly when installed, else basedpyright when installed, else off.

The backend's diagnostics are shown on the `.lpy` buffer: opening a buffer starts the backend, and a diagnostic that lands on code the buffer never spells (generated by `require`, `defmacro`, the prelude) is dropped; an error inside a macro's output is shown on the macro call. A buffer that does not parse or compile shows only that error. The `pythonDiagnostics` initialization option (default `true`) set to `false` turns them off, and the backend then starts only on the first request that needs it. A line comment of the running backend's tool, `; pyrefly: ignore[codeA, codeB]` under pyrefly or `; pyright: ignore[ruleA, ruleB]` under basedpyright, drops the backend's diagnostics of those codes that start on its line, and a bare `; pyrefly: ignore` / `; pyright: ignore` all of them (spaced as the tool takes it: `;pyrefly:ignore` and `;; pyrefly: ignore` work too); each backend honours only its own tool's comments, and lispython's own parse and compile errors are never suppressed. An ignore comment that suppresses nothing is never reported. Under basedpyright the rules follow the project's own `pyrightconfig.json`, else `[tool.basedpyright]`, else `[tool.pyright]` in `pyproject.toml`: `typeCheckingMode` (default `"standard"`), every `report*` rule and the `strict*` inference settings; path settings are ignored. Under pyrefly they follow the project's `pyrefly.toml`, else `[tool.pyrefly]` in `pyproject.toml` (its rule keys and `errors` table; path settings are ignored). A project with neither is checked with pyrefly's `"default"` preset, where `pyrefly check` alone would use `"basic"`, which hides nearly every type error; the server says so once per project when a buffer opens, and adding either config (e.g. `preset = "default"`) chooses the preset.

## nREPL Server
LisPython includes an nREPL server for REPL-driven development:

```bash
lpy --nrepl         # start on a random port
lpy --nrepl 7888    # start on a specific port
```

While running, the server writes its port to `.nrepl-port` in the working directory for editor auto-discovery.

The server accepts newline-delimited JSON over TCP and supports:
- `eval` — evaluate LisPython code, return value/stdout/error
- `load-file` — load a `.lpy` file into the session
- `macroexpand` — expand macros and return the result
- `complete` — prefix and dot-completion from the live scope, with a `kinds` map (class/function/variable/macro/keyword)
- `docs` — signature and docstring for a symbol
- `annotate` — type tag (function/class/module/macro)

### Editor setup

#### VS Code
Install the [LisPython](https://marketplace.visualstudio.com/items?itemName=jetack.vscode-lispython) extension. It connects to both LSP and nREPL automatically.

#### Emacs
Use [`lpy-mode`](https://github.com/jetack/lpy-mode). It provides nREPL integration (eval, completion, eldoc, macroexpand) and LSP via eglot.
