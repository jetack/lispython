# Changelog

All notable changes to lispython are documented here. The format follows
[Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and the project
follows [Semantic Versioning](https://semver.org/).

## [Unreleased]

### Added

- nREPL: stream evals and an `interrupt` op. An `eval` or `load-file` sent
  with `"stream": true` streams its output as `{"op": "out", "stdout": ...}`
  / `{"op": "out", "stderr": ...}` messages (in write order, promptly, with
  bounded buffering) before its final result, whose `stdout` is then empty.
  The connection keeps answering `complete`, `docs`, `macroexpand`,
  `annotate`, `ping` and `interrupt` while a stream eval runs.
  `{"op": "interrupt", "interrupt-id": X}` raises `KeyboardInterrupt` in the
  running eval `X`, stream or plain (its result's error is the traceback),
  or cancels it while it is queued (error `KeyboardInterrupt`), and replies
  `interrupt-result`. Evals of one connection run one at a time in request
  order; different connections run at once, each eval's output kept to its
  own connection. Without `stream`, an eval's output stays in its result.

- `(require mod as m)` registers every macro of `mod` as `m.name`, with a
  bare `as` as `import` takes. The LSP's completion after `m.`, hover and
  go-to-definition follow the alias, and a relative require's macros.
- nREPL: the `complete` reply carries `items`, LSP-shaped completion items in
  `completions` order: `{"label", "kind"}` with the LSP CompletionItemKind
  number, plus `"labelDetails": {"description": <tag>}` for a name lispython
  tags (`special form`, `macro`, `function`), exactly as the LSP server sends
  its own items. Labels are the LSP's too: only the part after the prefix's
  last `.` (`heapq.nl` offers `nlargest`, with the reply's new `word`, `nl`,
  the typed text a label replaces), and a name spelled as the evaluated code
  spells it when that is no hyphen spelling (`ok?`, `->foo`). Editor
  clients can read nREPL completion through their LSP path.
- nREPL: `eval`, `complete` and `macroexpand` take an optional `ns` (an
  absolute file path) that picks that file's scope only. Tracebacks and
  linecache keep the eval's `<nrepl-N>` name. `file` wins when both are sent,
  and an invalid `ns` (not an absolute path string) is an error reply.
- LSP: the Python backend's diagnostics now show in `.lpy` buffers, beside
  lispython's own. The backend is pyrefly (the `lsp` extra) by default, or
  basedpyright (the `lsp-basedpyright` extra; the default when pyrefly is not
  installed). Each lands on the `.lpy` text it is
  about; one on code the buffer never spells (generated by `require`,
  `defmacro` or the prelude) is dropped, and an error inside a macro's output
  lands on the macro call. Messages name things as the buffer spells them
  (`"undefined-name" is not defined`). A parse or compile error hides them
  until the buffer compiles again. Rule settings (path settings excepted)
  come from the project's own config for that backend: `pyrefly.toml` or
  `[tool.pyrefly]` in `pyproject.toml` (preset `default` when there is none
  or it cannot be read or pyrefly refuses it, which the server tells once
  per project, saying why), or `pyrightconfig.json` (JSONC)
  or `[tool.basedpyright]`/`[tool.pyright]` (`typeCheckingMode` `standard`
  when it sets none). A trailing `; pyrefly: ignore[code, ...]` under
  pyrefly, `; pyright: ignore[rule, ...]` under basedpyright (or a bare
  one) silences the diagnostics starting on its line; an unused one is never
  reported. Setting the `pythonDiagnostics` initializationOption (default
  `true`) to `false` turns them off; the backend then starts only on the
  first request that needs it (completion, hover, definition).
- A Pygments lexer for lispython (`lispy.highlight.LispythonLexer`),
  registered through the `pygments.lexers` entry point under the aliases
  `lispython` and `lpy` and the `*.lpy` filename, so Markdown fences, Sphinx
  and anything else highlighting through Pygments colour `;` comments,
  `:keyword` arguments, lispython's forms and built-in macros, Python's
  keywords and builtins, and f/t-string fields. It needs Pygments installed;
  lispython itself does not depend on it. The docs' code blocks use it.
- Built-in macros (`cond`, `conde`, `->`, `->>`, `as->`, `fn`, `comment`,
  `when`, `inc`, `dec`, `++`, `--`) are loaded in every module with no
  `require`: files, `lpy -m`, `lpy -c`, the REPL, nREPL, `l2py` and the LSP.
  The prelude emits no runtime code, so `(require mod *)` never re-exports
  them. A module opts out (or narrows) by making
  `(require lispy.macros <selection>)` its first form, after an optional
  docstring: `[-> ->>]` keeps only those, `[]` none, `*` all, and a bare
  `(require lispy.macros)` only the qualified names.
- nREPL: a file-less `eval` runs in the session's `__main__` scope with every
  built-in; an `eval` with `file`, or `load-file`, runs in that file's own
  macro scope. A `load-file` starts the file again: its macros are every
  built-in and nothing an earlier load defined, its first form's opt-out
  applies, and so it compiles as under `lpy`. An `eval` with `file` that
  sends `line` 1 (and `column` 1 or none) re-derives from its first form
  only the built-ins the file got without asking: an opt-out there drops
  them (its selection comes back), any other form brings back each one the
  file lacks, and the file's own macros and everything a `require`
  registered, built-ins included, stay, as re-evaluating a Clojure `ns`
  form keeps the namespace's vars. Any other `eval` with `file`, one without `line`
  included, only adds. `macroexpand`, `complete`, `docs` and `annotate`
  accept an optional `file` to answer from that file's scope.

### Changed

- nREPL: the server no longer waits for a plain eval before reading the next
  request, so an endless eval can be interrupted, and closing the client
  stops it, where before only killing the server did. A later non-eval
  request (`complete`, `macroexpand`, `docs`, ...) no longer waits for an
  earlier eval, so it may see the scope as it was before that eval, and its
  reply can arrive before the eval's result: match replies by `id`. An
  id-less eval no longer keeps reply order either, and its reply has
  nothing to match by. A plain eval reusing the `id` of one still queued
  or running is refused. A client that half-closes its socket after
  sending an eval (`shutdown(SHUT_WR)`, `nc -N`) usually loses the reply:
  EOF cancels or interrupts the connection's unfinished evals and shuts
  the socket down, so only an eval that finished first is sure to reply.
- `{` now ends a symbol, as `[` does, so a symbol can no longer contain `{`:
  `a{b}` reads as the symbol `a` and the brace form `{b}` (it was an
  unmatched `}`), and `x{` is an unclosed `{` (it was the symbol `x{`). A
  `{` never glues to the name before it. A number ends at `{` too: `1{2}` is
  the number `1` then `{2}`. The word boundary spec
  (`python -m lispy.word_boundary`) is version 4: `{` is in `stopChars`, and
  the new `numberEndChars` field is what may follow a number token.
- nREPL: an eval's output is captured per thread, no longer by swapping
  `sys.stdout` for the whole process. Output of a thread the evaluated code
  starts now goes to the server's own stdout/stderr, plain evals included,
  instead of into the eval's result.
- `lpy -m` names its module the way `import` does, so `ok?` and `->foo`
  run `ok_p.lpy` and `_to_foo.lpy` rather than a plain `-` to `_` swap's
  `ok?` and `_>foo`, and a part that is no name (a keyword such as `class`)
  is refused with a positioned compile error,
  `<command line>:1:1: error: ...`.
- LSP: a `.lpy` in a plain subdirectory of a workspace folder (no
  `__init__`) is named as a module of that namespace package
  (`scripts/tool.lpy` is `scripts.tool`, imported from the folder), so its
  `__name__`/`__package__` at compile time differ from before. It also
  stays the script `lpy scripts/tool.lpy` runs: its own directory (as `lpy`
  runs it) and its import root are searched by its compile, the local
  definition fallback and the backend alike, so a bare require or import of
  a sibling still resolves.
- LSP: a module inside a regular package (`src/pkg/m.lpy`, or
  `tools/mypkg/a.lpy` in a namespace directory) is analysed as
  `import pkg.m` sees it, with its import root alone: its own directory is
  no longer on `sys.path` while its macros run, so a bare sibling
  `(require helper)` there loads no macros (a "module not found" warning),
  as `import pkg.m` finds no `helper` either; write `(require pkg.helper)`
  or `(require .helper)`. The
  compile, go-to-definition and the backend now search the same
  directories.
- The `lpy` REPL and CLI no longer put the working directory's package root
  on `sys.path` or set the REPL's `__package__` to the working directory's
  package when `lispy.tools` is imported: `__main__` is in no package
  (`__package__` is `None`), as Python's own is.
- A relative `(require .mac)` (or `(require ..pkg.mac)`) registers its macros
  as `mac.name`, the name `from . import mac` binds, instead of `.mac.name`,
  which no code could spell. Code calling `(.mac.name ...)` must call
  `(mac.name ...)`. `(require .)` and `(require ..)` with no selection bind
  no name and are a compile error; give them `as`, `*` or a list.
- A `require` whose module is no symbol, `(require 1)` or `(require "m")`,
  is a compile error at it; it used to be a "module not found" warning.
- A relative `require` compiled with no package (a module outside any
  package; `lpy -c` or the REPL run from a directory that is no package) is
  a compile error at the module, "attempted relative import with no known
  parent package", instead of Python's bare `TypeError`.
- `require` imports a module by the name `import` gives it: `(require ok?)`
  imports `ok_p` and `(require ->foo)` `_to_foo`, as `(import ok?)` and
  `(import ->foo)` do, instead of `ok?` and `_>foo`. A malformed path
  (`(require mac.)`, `a..b`, `m.-`, `.mac.`) is a compile error at the
  module, worded as `from` words it.
- A `defmacro` no longer binds any name in the module that defines it. It
  used to star-import `lispy.core.nodes` and `lispy.core.builtins` there,
  overwriting the module's own `Paren`, `Symbol` or `gensym` and leaving
  `deque`, `atom_text` and the rest as module globals. A macro body now sees
  exactly `lispy.core.builtins.__all__`: the node classes, `gensym` and
  `replace_symbol`. Module-level code that used those names after a
  `defmacro` without importing them needs `(from lispy.core.builtins *)`, and
  a body that used another name of either module (`reset_gensym_counter`,
  `atom_text`, `deque`, ...) imports it itself. `(from lispy.core.builtins *)`
  itself now exports exactly `__all__` (the node classes, `gensym`,
  `replace_symbol`): it adds node classes such as `Brace`, `Constant` and
  `String`, and no longer exports `reset_gensym_counter`, which must be
  imported by name. `defmacro` now also works inside a function or class
  body.
- The operator `-` is no longer the Python name `_`: in a name slot (a value,
  an assignment or loop target, a parameter, an import, an attribute such as
  `a.-` or `(.- x)`, a keyword argument, a match capture, a slice operand) it
  is a compile error, "- is an operator and cannot be used as a name" or the
  slot's own "expects a name" error, exactly as `+` already was. `(- a b)` and `(- x)` are unchanged, and hyphenated operator
  names (`is-not`, `not-in`) stay the names `is_not` and `not_in`. A method
  head such as `(.+ x)` now gets the same operator message.
- A macro is called by either spelling of its name, as every other name is:
  after `(defmacro my_mac ...)`, `(my-mac ...)` expands it too, and the reverse;
  qualified names likewise (`mod.my-mac` is `mod.my_mac`), and so does a
  `(require mod [my-mac])` selection. Spellings such as `->`, `ok?` or `x-`
  stay only themselves.
- Defining a macro under the other spelling of an existing macro's name
  redefines it (the last definition wins), at compile time and in the
  module's runtime macro table that requirers read. It used to keep both as
  separate macros.
- nREPL: `annotate` answers `<macro name>` for a macro (it used to answer
  `<function name>`), and `docs`/`annotate` find a macro whose name has a
  hyphen (they used to miss it).
- nREPL: the `complete` reply no longer carries the `kinds` map. `items` is
  the only kind channel; `completions` (the bare names) stays.
- LSP: opening a `.lpy` file starts the Python backend while diagnostics are
  on (it used to wait for the first completion, hover or definition), and a
  buffer change compiles the buffer once, off the event loop (it used to
  compile on the loop, and again for a running backend).
- `(->> x f (g 1))` now compiles to `g(1, f(x))`: the steps after a bare-name
  step keep threading last (they used to thread first).
- `conde` with an even number of operands (no final else) is a compile error
  at the call; it used to drop its last test.
- **Breaking:** `def`, `async-def`, `class` and `defmacro` with no body
  (`(def f [])`, `(class A [])`, a body of only `(do)`, or a `def` holding only
  a return annotation) are a compile error at the form (`(<form> ...) needs a
  body`; a defmacro's names its generated `def`), as the equivalent Python is a
  SyntaxError. They used to compile to `pass`. Write the `pass` (or a
  docstring) explicitly.
- Built-in macros now load with no `require` (see Added), so a call to a
  function named like one (`inc`, `dec`, `when`, `fn`, `comment`, `cond`,
  ...) that the module did not bind itself, such as a name from
  `(from lib *)` or a Python builtin, now expands the macro instead of
  calling the function. Fix: make `(require lispy.macros [...])` the
  module's first form, listing only the macros it uses (`[]` for none).
- nREPL: an `eval` naming a `file`, and `load-file`, run in that file's own
  scope instead of the session's, so a file-less `eval` no longer sees the
  definitions they make. Editor clients should send `file` with `complete`,
  `docs`, `macroexpand` and `annotate` too, to answer from the same scope.
- `lispy.tools.src_to_python`, `src_to_python_org` and `l2py_s` called
  without a scope compile each source as a module of its own, in a new
  scope, instead of in the REPL session's shared `SCOPE`: a macro one call
  defines is no longer visible to the next, and a call no longer resets
  the session's macros. Pass `scope=` to `src_to_python(_org)` to share one.
- Upgrading: a `.pyc` that 0.6.0 compiled for a module using a built-in
  macro without a `require` keeps its old code until the source changes;
  touch the file or delete its `__pycache__`.
- Binding a name that is an active macro (`def`/`class` names, `=`,
  augmented assignment, `:=`, parameters, `defmacro` parameters and locals,
  `for`/`with`/`except`/comprehension targets, import names and aliases,
  match captures, type parameters) is a compile error, because macro lookup
  is by head name and `(inc ...)` would still expand the macro. A hyphenated
  name such as `my-x` is one name with `my_x`; any other spelling, such as
  `->` or `ok?`, clashes only with itself. The error names the macro as it
  is spelled. This refuses code that compiled before, for example
  `(def inc [x] ...)` or `(defmacro m [cond] ...)`. Rename the binding, or
  list only the macros the module uses in
  `(require lispy.macros [...])` as its first form. A `defmacro` of the same
  name stays allowed.
- A number-shaped digit-led symbol in a match pattern (value pattern,
  mapping-pattern key, class-pattern class name or `:attr` keyword:
  `(case 1.5if ...)`, `1.else`, `(1.5if)`, `(a.b :1.5if k)`) and a
  malformed number token as a class name (`(1else :a b)`) are now refused
  with the malformed-number message they get everywhere else ("invalid
  decimal literal"; `0x1for` gives "invalid hexadecimal literal"), instead
  of a pattern error ("pattern expected", "class pattern needs a class
  name", "class pattern expects an attribute name after :"). A class
  pattern's head is refused before its operands.
- On Python 3.11, a doubled brace in a format spec after a nested field is
  read as on every other version, a literal brace: `f"{x:{y}{{}"` compiles
  to the spec `{y}` followed by `{`, where it was an error.
- A line break in a single-quoted f/t-string's format-spec text, in any
  segment, is a compile error at the break on every Python version
  (`f"{x:ab\n}"`: "newlines are not allowed in format specifiers for single
  quoted f-strings"), as it was on 3.13+ only. This refuses source that
  compiled before: on 3.11 such a break was read as spec text
  (`f"{x:ab\nc}"`, `f"{x!r:\n}"`, `f"{x:{y:\n}}"` all compiled), and on
  3.12 the text after it was read as code. A backslash before the break
  (an odd run of them, raw literal or not) continues the line and is no
  line break (`f"{x:a\<newline>b}"`). A line break elsewhere in a field
  stands wherever code takes whitespace (`f"{x\n!r}"`, `f"{x:{\ny}}"`), except right after
  the `!`, and a triple-quoted literal's spec text keeps it as text. So does
  a backslash continuation in a field's code (`f"{(+ x\<newline>1)}"`
  compiles, as on 3.12+, where the backslash was lexed into a symbol). A source
  ending in format-spec text is the literal unterminated on every version.
- An f/t-string error is the first error in the source, on every Python
  version: nothing after it is read, so a later unterminated string or
  unmatched bracket no longer replaces it (`f"{x!z}" "b` reports the
  invalid conversion, where every version reported the string). A
  conversion is checked where it is read: an invalid name (`!z`) is refused
  at once, even where 3.12 and 3.13 reported an error later in the field
  first; with no name after the `!`, a `}` or `:` next is "missing
  conversion character", a `)` or `]` "unmatched ')'" or "unmatched ']'",
  and any other token (`f"{x!"a"}"`) "invalid conversion character", at
  that token, a quote there opening a string as anywhere in a field. A
  string prefix glued to the quote is part of that string, as CPython 3.14+
  read it: `!r"a"` and `!f"a"` are "invalid conversion character" at the
  prefix, an f/t-string's body unread; an invalid prefix (`!bt"a"`,
  `!ub"a"`) is refused at the prefix; a plain string that never closes
  (`!r"a`) is unterminated. A name of other letters, or repeating one, is a
  conversion (`!ra"a"`, `!rr"a"`: "invalid conversion character 'ra'").
  0.6.0 worded and placed these differently by Python version. Anything but
  blanks, `:` or `}` after the name is "expecting ':' or '}'"
  there. The literal's closing quote in a format spec is
  "expecting '}', or format specs" at the quote, the escaped `\"` literal
  included.
- On Python 3.12+, an error after a line break in a single-quoted f/t-string's
  text, or in a plain string spanning lines in a field, is reported where it
  is (`f"a\n}"`: "single '}' is not allowed" on line 2), no longer as the
  literal unterminated at the break.
- On Python 3.11, f/t-string errors are those of every other version: the
  error inside a literal at its own position (`f"{}"`: "valid expression
  required before '}'"), where 3.11 reported the whole literal as an
  unterminated string. An unterminated single-quoted string, plain or
  f/t, names the line the source ends on in "(detected at line N)" on every
  version (a lispython string may span lines), where it named the string's
  first line break; a final `\r\n` starts no line on 3.11 either.
- A plain string in an f/t-string field that never closes is "unterminated
  string literal (detected at line N)" at the string token, its quote the
  literal's or not, on every version; where its quote was the literal's,
  3.12+ reported "f-string: expecting '}'" (3.15: "... to close '{' on line
  N"). A name glued to the quote (`x"`) is part of the token, so the error is
  at the name.
- A starred assignment target outside a list or tuple (`(= *a 1)`) and two
  starred targets in one (`(= [*a *b] 1)`) are reported by Python's own
  compiler, with its message at the .lpy position; two starred are now
  positioned at the list or tuple rather than the second starred, and a bad
  target after them in the same assignment is reported first. On 3.15,
  `(lazy-from json *)` (shipped with `lazy-from` in 0.5.0) is likewise
  Python's own "lazy from ... import * is not allowed".

### Fixed

- Completion in an f-string field after text or in a format spec
  (`f"ab{wi`, `f"{x:>{wi`, `f"{a}b{c`) completes the field's name: the word
  no longer runs back through the field's `{` into the text or spec before
  it, in the LSP and in every editor following the word boundary spec.
- LSP: go-to-definition without a backend resolves a relative module, of a
  `require` or a `from`, as Python does: in the document's package, never
  beyond its top-level package, and not at all for a buffer with no file.
  A document path with a space or a non-ASCII character is read decoded.
  It finds a module by the name its import takes, so `(from ok? [x])` and
  `(import ->foo)` reach `ok_p.lpy` and `_to_foo.lpy`, and it picks the
  file Python imports: a built-in or frozen module, then a package's
  `__init__` (of any suffix) before a module file of the same name, and
  nothing when that file is no `.lpy`, except a regular package that holds
  an `init.lpy` (the layout of `lispy.macros`), which answers with that
  file. Every dotted part is looked up as Python's import looks it up (its
  FileFinder and path hooks, and the `sys.meta_path` finders an editable
  install adds), so a module Python imports from the workspace that is no
  `.lpy` is never replaced by an installed one. The lookup itself imports
  nothing, for go-to-definition and the index of a file's requires alike,
  and it consults only the import hooks Python consults after its own path
  search.
- The LSP and the nREPL resolve a relative `require` or `from` in a
  namespace package (a directory with no `__init__`) as the importer does:
  `ns/a.lpy` is `ns.a`, so `(require .mac)` compiles and go-to-definition
  finds `ns/mac.lpy`. The LSP counts namespace packages up to the nearest
  of the document's workspace folder and its `src`; the nREPL up to the
  nearest `sys.path` entry as the server started. A directory that is no
  identifier, or has a module file of its name beside it, is no namespace
  package.
- A malformed `require` (`(require mod a b)`, `(require mod as)`,
  `(require mod * as m)`, `(require)`, a non-name in its list) is a compile
  error at the part at fault, instead of a Python `ValueError` or
  `TypeError` with no position.
- `l2py` translates as deep as `compile()` takes (statements, expressions,
  match patterns, nested f-strings and format specs), with the text
  `ast.unparse` would write, instead of stopping at a few hundred levels
  (about 250 nested statements, patterns or format specs, 100 nested
  f-strings) with "form nested too deeply to translate". That error remains
  only for a caller whose own stack is already near the recursion limit. The
  LSP's Python view likewise builds for buffers nested past `ast.unparse`
  (they previously got no view, so no backend diagnostics, hover or
  completion from the Python backend).
- A body that compiles to no statement, such as `(when test)` or
  `(if x (do))`, is a compile error at the form (`(if ...) needs a body`)
  for `if`, `while`, `for`, `with`, `try`, `except`, `else`, `finally` and
  `case`, where it printed `if x:` with nothing under it.
- An invalid escape in a string (`"\d"`) warns at the .lpy file and line of
  the string, where it named `<unknown>` line 1.
- A malformed number glued to a keyword (`(= a 1if)`, `0x1for`, `1jor`) is
  CPython's "invalid decimal literal" ("invalid hexadecimal literal",
  "invalid imaginary literal", ...) at the token, where it said "invalid
  syntax" and 0.6.0 also printed a stray "<unknown>:1: SyntaxWarning:
  invalid decimal literal"; a digit-led symbol (`1.else`, `1__0`) says the
  same where it said "is not a valid Python name". A number token Python
  reads as two (`406E-9.8J`) is "invalid number literal" at the token, where
  it said "invalid syntax".
- Modules shared one process-wide macro namespace, so whether `inc` worked
  without a `require` depended on the bytecode cache and one module's
  `defmacro`s could leak into another. Each module now has its own macro
  scope, and `defmacro` and `require` bodies expand in their own module.

## [0.6.0] - 2026-11-02

### Added

- The nREPL `eval` op reads the standard `file`, `line` and `column` fields
  (where the code sits in the editor's buffer, 1-based). Tracebacks and
  compile errors then name that file with buffer line numbers and print the
  source line, including for definitions evaluated in earlier requests and
  for `load-file`.
- `(raise)` compiles to a bare `raise`, re-raising the exception being
  handled.

### Changed

- A string opened with `\"` in an f/t-string replacement field must be closed
  by `\"` (`\"\"\"` for `\"\"\"`): a bare `"` in it, as its close or its
  content, is a compile error at the opener, where it was accepted before
  (`f"{(g \"a")}"`). Its `{x=}` echo (and a t-string's expression text) now
  shows the source as written: `f"{(.get d \"k\")=}"` echoes
  `(.get d \"k\")=`, where it echoed `(.get d "k")=`.
- On 3.12 a single-quoted literal's format spec continued after a line
  break in its text is read as CPython 3.12 reads it: the line break and
  what follows are no longer part of the spec (`f"{x:ab\n}"` formats with
  `ab`, where it used `ab\n`), only blanks, comments and replacement fields
  may follow before the `}`, and any other text there (`f"{x:a\nb}"`, which
  was accepted) is CPython's "expecting '}', or format specs" error or its
  tokenizer error.
- An nREPL eval without `file` is named `<nrepl-N>` (a new N per eval)
  instead of `<nrepl>`, which can break a client that matches `<nrepl>` in
  error text.
- On Python 3.13+, a line break in a single-quoted f/t-string's format spec
  is a compile error at the break even when the field then closes
  (`f"{x:ab\n}"`), as CPython 3.13+ refuse it; it compiled before.
- An invalid `line` or `column` (not an integer from 1 to
  `NREPL-MAX-POSITION-LINE`, 1,000,000, or `NREPL-MAX-POSITION-COLUMN`,
  100,000) gets an `error` reply with the request id instead of being
  accepted.
- Every name the compiler emits must be a Python name, or it is a compile
  error at the symbol. Code that compiled and ran before is now refused:
  a symbol whose mangled text is no Python identifier (`foo!`, `a.`, as in
  `(= foo! 1)`), an operator whose mangled text is no identifier used as a
  value (`(f +)`, `(print ~)`), and a hard keyword in any name slot:
  attributes (`(. a if)`, `(.if x)`), keyword arguments (`(f :if 1)`, class
  keywords), parameters (`(def f [:if 1] ...)`), type parameters, import
  names and aliases, match captures and class pattern attributes. CPython
  compiled such names from the AST, but no Python source spells them, so
  `l2py` printed code that does not parse. Operators that mangle to a name
  (`-` is `_`, `is-not` is `is_not`) are names as before.
- An attribute slot takes one name: `(. a b.c)` and `(.a.b x)` are compile
  errors; write `(. a b c)` and `(.b x.a)`.
- `(. a)`, an attribute form with no attribute, is a compile error in every
  context (value, assignment, `del`, annotated and augmented targets); it
  used to compile to the plain name `a`. Write `a`, or `(. a b)` for an
  attribute.
- A hard keyword called in an expression (`(f (else 1))`) is reported as
  `else is a Python keyword and cannot be used as a name`, at the keyword,
  instead of `else is a Python keyword and cannot be called` at the form.
- Forms that compiled to something other than what they say are compile
  errors: `(ife a b c d)` (dropped `d`), `(yield a b)`, a comprehension clause
  with a stray or dangling operand (`[x for y in z if]`, `(x for y in z if a
  b)`), and a parameter list CPython refuses: a misplaced
  or repeated `/`, `*` or `**kw` (`[a / /]` dropped `a`, `[*a *b]` made `b`
  keyword-only), a bare `*` with no keyword-only parameter, and `[a :b 1
  c]`, which compiled to `def f(a, b, c=1)`. An annotated lambda parameter (`(lambda [a ^int] 1)`, which `l2py`
  printed as `lambda a: int: 1`) is refused too.
- Class bases are read as call arguments: `(class A [**kw])` compiles to
  `class A(**kw)`.
- A statement form (`do`, `=`, `if`, `return`, ...) in expression position is
  now a compile error instead of emitting an invalid call such as `do(...)`.
  A Python function named `do`, `deco`, `async_def`, etc. can no longer be
  called with lispython call syntax in expression position; they were already
  unreachable as statements.
- A Python hard keyword in call position (e.g. `(not a b)`, which used to
  compile to `not (a, b)`, silently false, or `(else ...)`) is now a compile
  error.
- Statement forms that compiled while dropping part of what was written are
  now compile errors: `(deco d (f))`, whose definition is not a `def`,
  `async-def`, `class` or `deco` (the decorator was silently dropped);
  `(assert a b c)` (the third operand was ignored); a form other than
  `(case ...)` inside `match` (it was read as a case); and def arguments or
  class bases written as anything but a `[...]` bracket (`(def f (x) ...)`
  compiled). A `case` with `as` after its guard (`(case 1 if g as y ...)`,
  which compiled `as y` into the body) is refused: `as` comes before `if`.
- A `;` ends a symbol or number, so a comment needs no space before it:
  `a;c` was the symbol `a;c`, now `a` followed by a comment.
- A Python hard keyword as a symbol name, or as a part of a dotted symbol,
  is a compile error: `(raise from)`, `(= o.if 1)` (which compiled to an
  attribute named `if`), and a keyword as a def, class, global, nonlocal,
  `case ... as` or `except [... as]` name (`(def if [] 1)`,
  `(case 1 as as ...)`).
- `~` directly before a closing bracket, a comma, `;` or the end of input
  (`(f ~)`, `(f ~,a)`, `~;c`) is the symbol `~`, as before a space, instead
  of an unquote that took the next form or gave "unmatched ')'".
- A dotted name in a case pattern (`(case Color.RED ...)`) is a value
  pattern, compared with `==` as in Python. It compiled to a capture pattern
  that matched every subject, so code that relied on that now falls through
  to the next case.
- A `()` in a case pattern whose head is an expression form (`(sub x)`,
  `(ife a b c)`, `(is-not x)`, `(not-in x)`) is a compile error ("pattern
  expected") instead of a class pattern on a class of that name.
- A sign before anything but a number in a case pattern (`(- a)`, `{-a 1}`)
  reports "pattern can sign only a number literal, got (- a)" with the
  pattern usage, instead of "only a number literal can be signed in a match
  pattern".
- An f/t-string format spec reads braces as CPython does: `}` always ends
  the spec and `{` opens a nested field, so `{{` and `}}` are no escapes
  there, except that on 3.12+ `{{` is a literal `{` once a nested field has
  opened in the spec. `f"{x:{{}}}"`, which formatted `x` with the literal
  spec `{}`, is now `x` with a spec field holding `{}`, and `f"{x:{y}{{}}}"`,
  whose spec was `{y}` then `{}`, has the spec `{y}` then `{` followed by a
  literal `}` on 3.12+ (a spec field `{}` on 3.11).
- The operand after `^`, `*`, `**` or `:` keeps its own token type, so `*1`,
  `**1`, `:1` and `^1` read a number `1` instead of a symbol named `1`. A
  keyword with a number or other non-name after it (`(f :1 x)`, `(def g [:1
  2] ...)`) is a compile error at it, a bare `:a` or `**x` used as a value
  (`(= x :a)`, `[**1]`) is a compile error instead of silently the name `a`
  (or a raw `AttributeError`), and a trailing `:a` with no value in a call,
  def or class argument list is a compile error instead of a raw `IndexError`.
- Threading a literal into a call (`(-> 1 (f))`, `(->> 1 (f 2))`,
  `(-> "a" (f))`, `(-> ... (f))`) compiles to `f(1)`, `f(2, 1)`, `f('a')`
  and `f(...)` instead of failing with an `AttributeError`, and
  `(-> None (f))`, which compiled to `f()`, now gives `f(None)`. A macro may
  put Python values (`None`, booleans, numbers, `...`, str, bytes, and
  lists and tuples of them) anywhere in the forms it returns, including
  inside `*`, `**`, `^` and quote forms (`` `(list *~y) ``); each compiles
  to the same value (including `inf`, `nan`, `-0.0`, complex numbers with a
  signed zero, `inf` or `nan` part and ints of any size) at the macro
  call's position, even where `float` or `complex` is rebound or inside a
  match pattern. Converting nested lists does not recurse, so deep nesting
  does not hit `RecursionError` there. Any other value (a dict, a set, an
  object), or a form or list that contains itself (also one unquoted with
  `~`), is a compile error at the call naming the macro.
- A str a macro returns keeps its backslashes literally: `"a\\b"` was
  compiled as `"a\b"` (backspace), and a quote, line ending or control
  character is kept as written. The same holds for quoted strings and
  quoted symbols (`'a\b` was `Symbol('a\x08')`); bytes are supported.
- An assignment, augmented assignment, `del`, `for` or `with ... as` target
  that Python cannot bind (`(= 1 2)`, `(= (f) 1)`, `(+= [] 1)`, `(del *a)`)
  is a compile error at the target with CPython's message ("cannot assign to
  literal"), and so is an annotation anywhere but right after a single
  target (`(= ^int 1)`, `(= a b ^int 1)`) or a def/class name that is not a
  name (`(def [] [] 1)`, `(class 1 [])`).
- A quote, quasiquote or unquote-splice with no form right after it
  (`(f ' a)`, `(f *' a)`, `(f ~@ a)`, `(f ')`, `',a`) is a compile error at
  the quote instead of a symbol `'`, `f(*', a)`, an unquote of `@` or
  "unmatched ')'". `~` alone is still the invert operator.
- A malformed `match` case pattern is a compile error at the part at fault,
  quoting the usage of its kind (class, mapping or sequence pattern, `(| ...)`),
  instead of an `IndexError`, `ValueError` or `AttributeError` or an AST
  that means something else: a dangling `:attr` (`(P :x)`), a positional
  pattern after a keyword one (`(P :x 1 2)`, which compiled to `P(2, x=1)`),
  a mapping key without a pattern (`{"a"}`), `**rest` not last (`{**r 1}`),
  `**_` (the rest must be a capture name), a key that is no literal or
  dotted name (`{a 1}`), a second `*rest` (`[*a *b]`), `*rest` outside a
  sequence (`(case *a ...)`), `(| 1)`, a class pattern head that is no name
  (`(1)`, `((f) 1)`), a `()` that is no call (`(+ 1 2)`, `(, a b)`,
  `f"x"`), `...` and a `:x` keyword token as a pattern.
- A name after `*`, `**` or `:` in a case pattern that is no Python
  identifier (`[*1a]`, `{**1a}`, `(P :1a 2)`) is a compile error instead of
  an AST naming `1a`.
- A malformed dotted name in a case pattern (`.x`, `a..b`, `x.`), as a value
  pattern, a mapping key or a class pattern head, is a compile error instead
  of an attribute with an empty name.
- A string opened with a bare quote inside an f/t-string replacement field
  reads as Python reads it: `\"` in it is an escaped quote and its
  backslashes are kept. `f"{(g "a\" b \"c")}"` compiles to
  `f"{g('a" b "c')}"`; it used to turn every `\"` into `"` before parsing
  the field, which split the string into `g('a', b, 'c')` or refused it
  (`f"{(g "say \"hi\"")}"`: "invalid string prefix").

### Deprecated

- Writing a string in an f/t-string replacement field with `\"`
  (`f"{(.get d \"k\")}"`) is deprecated: each such string emits a
  `SyntaxWarning` at its opening `\"`, shown by default (as CPython
  3.12+'s invalid escape sequences are). Write plain quotes
  (`f"{(.get d "k")}"`), which works on every supported Python. A
  warnings filter that turns it into an error
  (`PYTHONWARNINGS=error::SyntaxWarning`) makes it a compile error at the
  opener.

### Fixed

- A replacement field whose expression starts with a bare `=` (`f"{=}"`,
  `f"{=x}"`, `f"{=!r}"`, a source ending at `f"{=`) is refused with CPython
  3.12+'s "valid expression required before '='" at the `=`, as compile() does
  there. On 3.11 lispython reports that same 3.12+ message for a closed
  literal, as it does for `f"{}"` (CPython 3.11's own wording differs); a
  source ending inside the literal gets 3.11's whole-literal error. Before, a
  closed literal was refused only by the compile step ("= is not a valid
  Python name") or as a missing conversion (`f"{=!}"`), and on 3.12+ `f"{=`
  gave "'{' was never closed" and `f"{=}` "unterminated f-string literal".
  It is now refused when the source is read, so also inside quoted code.
- On 3.12+ an error after a line break in a single-quoted f/t-string's text
  (`f"a\n}"`, `f"a\n{x!z}"`, `f"a\n{)`) reports CPython's "unterminated
  f-string literal (detected at line N)" for that literal, as `compile()`
  does, whether or not the literal later closes: CPython's tokenizer stops
  at the break. A multi-line literal with no error still compiles.
- A comment ends at a lone CR as at LF and CRLF, as in CPython. A CR-only
  source (`; c\r(f 1)`) used to lose every form after a comment.
- A source ending inside a string, an f/t-string, a replacement field's
  expression, a format spec or a conversion reports the error `compile()`
  raises for that text on the running Python: "unterminated ... literal
  (detected at line N)" at the literal's prefix, 3.12+'s "'(' was never
  closed" (or "'{' was never closed") at the innermost bracket or field
  brace still open,
  "expecting '}'" for a string whose quote closes the
  literal it is in, 3.13+'s "newlines are not allowed in format specifiers",
  3.15's "expecting '}' to close '{' on line N", and 3.11's whole-literal
  error. A name glued to a quote after `!` reads as a string prefix (`!r"`),
  and an invalid conversion name is reported at the name, after any error in
  its field's format spec where CPython checks it only once the field closes.
- An f/t-string's closing quote inside a format spec (`f"{x:{y}"`) reports
  CPython 3.12+'s "expecting '}', or format specs" at the quote.
- An empty replacement field ("valid expression required before '}'") is
  reported where CPython 3.12+ report it: at the `}`, `!`, `:` or the `=` of
  `{ = }`, not at the field's `{`. A missing conversion (`f"{x! }"`) is
  reported at the token after the `!`, not at the `!`.
- An error in an f/t-string's field (an empty expression, more than one
  expression, a missing or invalid conversion, a token out of place after
  `!`) gives way, as in CPython, to a later tokenizer error outside any
  literal, such as a string that never closes: `f"{x!z}" "b` and
  `f"{a b}" "c` report "unterminated string literal" at the last string. On
  3.11 a later f-string that never closes does too. On 3.12+ a closing
  bracket out of place in a field after the error keeps it (`f"{x!r y)}" "b`),
  and one right after a conversion is CPython's "f-string: unmatched ')'".
- Error positions count a lone CR as a line break, as CPython does (CRLF is
  one break), so a source with CR line endings reports the same line as
  `compile()`.
- Parsing no longer spends Python frames per nesting level, so these parse
  at any depth and from a deep caller stack instead of raising
  `RecursionError`: f/t-strings nested in each other's fields, format specs
  nested in format specs, brackets nested deep inside one replacement
  field, and long prefix chains on one token
  (`^^^x`, `:::x`, `***x`, `^*^*x`), also glued to a bracket (`^^^a[int]`).
- Quasiquoting f-strings nested in each other's fields checks each field for
  an unquote once, linear instead of quadratic in the nesting (4,000 levels
  took 15 s), and a deep nest of `(do ...)` statements compiles in linear
  time.
- Deeply nested forms compile in time linear in their nesting: a nested list
  (`[[[...]]]`, also inside a macro call such as `when`) was exponential (20
  levels took seconds) and a form in head position (`((((f))))`) quadratic.
  Rendering a form and expanding macros no longer recurse, so a form nested
  past Python's recursion limit renders and expands.
- A long run of digits that is not a number lexes in linear time instead of
  quadratic.
- Forms nested deeper than about 245–330 levels (case patterns about 490)
  are no longer refused with "form nested too deeply to compile": the
  compiler and quote expansion no longer spend Python frames per level, so
  nesting compiles as deep as CPython's compile() takes (about 10,000
  Python AST levels on 3.12/3.13, more on 3.14+; forms that cost two AST
  levels per lispython level, such as keyword arguments, starred arguments
  and method calls, stop near half that). On 3.11 compile() itself still
  stops near the recursion limit, with the positioned error below. `l2py`
  still stops at a few hundred levels, because `ast.unparse` recurses: that
  is the positioned error "form nested too deeply to translate".
- Nesting past compile()'s own limit is the positioned "form nested too
  deeply to compile" error from `lpy`, imports, the REPL, nREPL, `defmacro`
  and `require`, instead of a `RecursionError` traceback, at the bottom of the
  deepest path in what compile() was given: for `lpy` files and imports the
  first statement that fails to compile alone (the whole module when each
  fits alone), the whole form for `defmacro` and `require`, and the statement
  compile() fails on for `lpy -c`, the REPL and nREPL. Its message names
  Python's recursion limit only where that is the limit hit (3.11, and
  `l2py`), since raising it does not move compile()'s limit on 3.12+. A
  macro's own runaway recursion still raises `RecursionError`.
- Data a macro puts in its expansion, spliced with `~x` or placed in a
  form's list, that holds the same Python list or tuple in many places is
  converted to nodes in time linear in the distinct data, instead of
  exponential in the depth of the sharing. Compiling such data still emits
  each shared value where it appears.
- A malformed expression form is a positioned compile error quoting its
  usage instead of an IndexError, ValueError or AssertionError, or an AST
  CPython rejects: `(:=)`, `(:= a ^int 1)`, `(.)`, `(.foo)`, `(ife a)`,
  `(sub)`, `(lambda [a])`, `(await)`, `(yield-from)`, `(and)`, `(< a)`,
  `[:]`, `{1 2 3}` and `(x for y)`. Hover and signature help for these forms
  show the same usage line.
- `(= (sub a) ^int 1)` records `a` in `__annotations__`, as `(= a ^int 1)`
  does.
- `~x` or `~@x` outside a quasiquote is a compile error at it (`~ (unquote)
  is only allowed inside a quasiquote`) instead of a raw `ValueError`.
- A comprehension target that cannot be assigned (`[x for 1 in xs]`) and a
  walrus target that is not a name (`(:= a.b 1)`, `(:= 1 2)`) are compile
  errors with CPython's messages (`cannot assign to literal`, `cannot use
  assignment expressions with attribute`) at the target, instead of a raw
  `ValueError` or `TypeError`.
- `(case pattern as _ ...)` is a compile error at the `_` (`cannot use '_'
  as a target`, as in CPython) instead of a raw `ValueError`.
- A dotted `defmacro` name (`(defmacro a.b ...)`) is refused as
  `(defmacro ...) expects an undotted name, got a.b`, at the name, instead
  of an error about the internal `___defmacro_temp___a.b` def.
- LSP hover and signature help for a statement form show the same usage
  line as the compiler's error messages (`(def name [args] body...)`,
  `(for target in iterable body...)`), and now cover the `except`,
  `except*`, `else`, `finally` and `case` clauses, augmented assignment
  (`+=` and friends), and `|` as an or-pattern. For `|`, hover and signature
  help show both the bitwise-OR operator and the or-pattern usage.
  Completion now also lists the augmented assignment operators and the
  `except`, `else` and `finally` clauses as special forms (`except*` and
  `case` were already offered as keywords).
  Hover text for `defmacro`, `lambda` and `fn` says `[args]`, matching `def`.
- A complex number a macro returns shows in macroexpand output as `1+2j`
  instead of `(1+2j)`, which read back as a call, not a number. A negative
  nan (alone or as a complex part) shows as `(- (float "nan"))` instead of
  losing its sign.
- A macro whose expansion puts Python data in a form's list compiles when
  another attribute also holds that list, and when the form's list is a
  tuple or deque, instead of failing with `AttributeError: 'int' object has
  no attribute 'name'`. A form's list of any other type (a dict, a set) is a
  compile error at the macro call naming the macro.
- Code a macro builds (from a quasiquote template) takes the position of the
  macro call, so a traceback or compile error in it points at that call
  instead of line 0; arguments written by the user keep their own positions.
- nREPL eval tracebacks no longer include the server's own `nrepl-eval`
  frame.
- The nREPL server buffers bytes and decodes each complete line, so a
  multi-byte UTF-8 character split across two socket reads no longer drops
  the connection. An unknown op, a malformed request or a failing handler
  (such as `eval` without `code`) now gets an `error` reply echoing the
  request id, and the connection keeps serving; a line that is not valid
  UTF-8 or JSON (or JSON that is not an object, or is nested too deeply to
  parse) gets an id-less `error` reply. A result that cannot be
  serialised is an `error` reply too, `(exit)` in an eval is reported as a
  `SystemExit` eval error, and any socket error ends the connection quietly.
  A request line over 4 MiB gets one id-less `error` reply and is dropped up
  to its next newline, so a client that never sends a newline cannot grow the
  server's memory; the connection keeps serving.
- `as->` expands to an expression (a tuple of `:=` assignments indexed with
  `-1`), so it works in expression position such as a `return` value or a
  call argument instead of emitting an invalid `do(...)` call.
- `as->` renames only references to the threading name: a keyword-argument
  name (`(f :x x)` was `f(__x_0=__x_0)`, now `f(x=__x_0)`) and the params
  and body of a `fn`/`lambda` that binds the same name are left alone (its
  defaults are still renamed), and `~x` inside a quasiquote now gets the
  threaded value.
- `as->` also renames a dotted reference (`x.real` becomes `__x_0.real`) and
  a reference inside an f-string format spec (`f"{1:{x}}"`).
- A `for` or `while` with no target, iterable or test, or with no body
  before its `(else ...)` (`(for x in)`, `(for [x [1]] (print x))`,
  `(while x)`), is a compile error at the loop instead of an `IndexError`
  or a loop with an empty body that Python rejects.
- `^` followed by stars before a bracket or a quote (`^*(`, `^**[`, `^*'`,
  `^**~`, also with a space after the quote) or alone (`^*`, `^**`) is a
  compile error at the prefix instead of a `KeyError`, an `AttributeError`
  or a call such as `f(*', a)`; `^*Ts` and `^**P` are unchanged.
- Every malformed statement form is a compile error naming the problem and
  the form's usage, at the form, clause or operand at fault, instead of a
  `ValueError`, `IndexError`, `AssertionError`, `TypeError` or an AST that
  Python rejects: `if`, `def`, `class`, `with`, `try` and its clauses,
  `match` and `case`, `deco`, `raise`, `assert`, `=`, augmented assignment,
  `del`, `global` and `nonlocal` with missing parts (`(if x)`, `(def f)`,
  `(with [a])`, `(try (f))`, `(match x (case 1))`, `(= x)`, `(global)`, ...),
  extra parts (`(raise a b)`, `(= x ^int 1 2)`) or a dangling `as`
  (`(with [a as] ...)`, `(except [E as] ...)`). A `try` clause out of order
  (except after else or finally, except mixed with except*, a form after
  the clauses) is reported at that clause instead of as "except is a Python
  keyword".
- An empty `()` is a compile error at it ("use (,) for an empty tuple")
  instead of an `IndexError`, wherever it appears.
- Installing lispython no longer puts a `test` command (pytest's entry point)
  on `PATH`.

## [0.5.0]

### Added

- Python 3.11 through 3.15 support, with each newer AST form gated on the
  running interpreter and a clear compile error on older ones. A `nox` matrix
  (`uvx nox -s tests`) runs the suite on every supported version.
- Type aliases: `(type NAME value)` compiles to a `type NAME = value`
  statement (3.12+). The three-operand `(type name bases ns)` call is unchanged.
- Generic definitions: `def`, `async def` and `class` names accept glued type
  parameters such as `f[T]`, including `ParamSpec`, `TypeVarTuple` and
  defaults (parameters 3.12+, defaults 3.13+).
- t-strings compile to `TemplateStr` (3.14+).
- `lazy-import` and `lazy-from` (3.15+).
- Comprehension unpacking (3.15+), including `{**d for d dicts}`, which was
  mistranslated as a dict display; unary plus is gated to 3.15+.
- Errors the CPython compiler raises on `.lpy` modules, and lispython's own
  compile errors, are reported with the file, line and caret instead of a
  traceback by `lpy` (file, `-m`, `-c`), `l2py`, the REPL and nREPL eval.
- LSP: `textDocument/signatureHelp` and `workspace/symbol`; `(type NAME ...)`
  aliases are indexed as definitions.
- nREPL: completion responses carry type kinds, and the server writes
  `.nrepl-port` in the working directory for editor auto-discovery.

### Changed

- **The REPL and nREPL compile every statement of an input before running any
  of it**, and `lpy -c` compiles its whole input first. A compile error,
  lispython's or CPython's, now stops the input before any statement runs
  (macro expansion still happens first); a `SyntaxError` the program raises
  at run time keeps its own traceback.
- **Stricter parsing** rejects input that used to be accepted silently: an
  unclosed final form or mismatched closing bracket, an unterminated string,
  an f-string field holding more than one form, a lone `}` in an f-string,
  non-symbol macro names (`(defmacro m[T] ...)`), `(import "x")`,
  `(lazy-import "numpy")`, `(return a b)`, and `name[...]` glued under a
  prefix such as `^list[int]` in a parameter list. Malformed literals such as
  `09` or `\x4` are reported at their token.
- **Literal values**: `-1+2j` is now `(-1+2j)` rather than `-(1+2j)`; `\r\n`
  and lone `\r` become `\n` in f-strings too; a multi-line raw string no
  longer gains a literal `\n`; backslash-newline continues a string; a lone
  `"` inside `"""..."""` no longer ends the token.
- **F-strings follow Python's rules.** An uppercase `F` prefix (and `rf`,
  `fR`, ...) is a real f-string rather than being evaluated at compile time,
  `{x=}` echoes the expression text and defaults to `!r`, and format specs
  may nest replacement fields (`{x:>{w}.{p}}`). Unquotes expand inside
  f-string and t-string fields.
- **`(require mod [])` registers no macros**, like an empty import list; only
  an absent list (`(require mod)`) registers all of them. The LSP follows the
  same rule in go-to-definition and hover.
- `lpy -m` puts the current directory on `sys.path` like `python -m`,
  honouring `PYTHONSAFEPATH`.
- Requires `pygls` 2.0 or later.

### Fixed

- `(return [])` compiled to a bare `return` (yielding `None`); it now returns
  the empty list.
- `(case {})` accepts an empty mapping pattern.
- Signed literal match patterns: `(case -1 ...)` compiled to `case _(1):`.
- `(from . [a])` compiles; it raised `IndexError`.
- Quasiquoted f/t-string fields keep their conversion, spec and `=` text
  (`f"{x!r:>6}"` used to come back as `{x}`), and `f"{~x}"` with a literal
  macro argument no longer crashes.
- `l2py` emits valid Python for t-string interpolations.
- A lone starred subscript slice compiles to a one-element `Tuple`, like
  Python's `t[*s]`.
- LSP: workspace symbols no longer include installed packages or function
  locals, and report their real kinds; a buffer that is mid-edit keeps
  working; signature help is not offered inside a quoted form.
- nREPL: completion kinds treat scope bindings as shadowing builtins, never
  run user code to classify attributes, and report callables as functions;
  an unwritable `.nrepl-port` no longer stops the server.
